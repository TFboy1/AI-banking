# 显式DAG任务执行：第一版

DAG是有向无环图。节点代表具体业务步骤，箭头代表前置依赖。“显式”表示这些节点、依赖和状态真的保存在后台，供调度器检查，不仅是模型写在回答中的计划。

例如：查询账户和查询银行卡是独立分支；创建新账户依赖两项查询成功；创建后查询账户依赖创建回执。节点未成功、等待用户确认、失败或取消时，其依赖步骤不允许开始。

## 当前接入方式

1. 模型按现有工具协议提出本轮具体步骤，继续使用工具返回的真实编号与参数。未知信息仍需查询或追问。
2. `task_dag.add_calls`在执行前生成并验证依赖图。同一轮白名单内的纯查询可以独立；变更和其他可能有关联的工具形成保守依赖屏障；下一轮依赖前一轮结果。
3. `task_dag.validate`检查重复节点、缺失依赖、循环依赖和节点数量上限。
4. `task_dag.select`只能选取全部前置节点成功的待执行节点；不能仅靠队列顺序绕过依赖。第一版实际执行仍逐步处理，暂不并发调用银行业务。
5. 图保存在每个任务SQLite `tasks.state_json.dag` 中，使用当前事务持久化；包含节点编号、工具、名称、依赖、执行状态、时间和回执编号。原有工具消息和审批记录保存参数、结果，并通过调用编号对应。
6. 确认卡等待时节点为`waiting_confirmation`，确认和原有支付验证通过、真正取得回执后才变成`succeeded`。失败停止后续执行，取消保留已经成功的节点。
7. SSE任务事件包含图的当前状态。页面展示可折叠的“处理步骤”，标明依赖和状态；刷新从bootstrap恢复最近任务图。也可通过已登录的`GET /api/tasks/{task_id}/plan`查看当前用户的图。

## 第一版边界

- 这是增量规划：每轮工具调用先落图再执行，根据查询结果和用户确认继续扩展，不会在任务刚开始就假定所有收款人、金额和报价已知。
- 不新增资金自动执行权限；既有密码、短信、确认和风险校验继续生效。
- 图的持久化不等于自动恢复执行。服务重启仍停止中断任务，保留已执行回执，不自动重放变更。
- 运行中停止已接入：取消当前处理并保留已执行回执，生成资金核对报告。尚未实现失败后重规划/恢复、补偿和人工接管。
- 不展示模型隐藏推理；步骤来自实际工具调用与业务执行结果。

后续可增加完整的结构化计划提案协议，由模型声明业务子目标与依赖，后台校验后再把节点绑定为具体工具。需要同时设计缺参等待、输出引用和计划版本变更，不能让模型通过计划绕过工具白名单及支付验证。
