# 银行业务框架与本次订阅修复

本次从订阅文字匹配补丁调整为“模型整理参数、后台查询和计算、确认后变更”的可扩展结构。不是为每种问法增加一个固定回答。

## 当前运行路径

1. Agent 只把当前会话最近的消息与当前请求送给模型；历史用于理解对象指代，不能授权新操作。手机号继续脱敏。
2. 模型从统一注册表选择业务工具，并输出受 Pydantic 约束的结构化参数。例如 `quote_subscriptions(services=["office"], months=24, inquire_packages=true)`。
3. 后台校验参数和会话对象依据，读取最新 SQLite 记录，用整数分计算金额。订阅报价不通过关键词规则解析期限。
4. 查询工具返回事实、记录编号、计算公式、资料缺失说明和界面数据。模型可以继续查询其他期限或其他业务；纯订阅报价的最终金额文本使用后台核对结果。
5. 变更工具继续创建待确认卡片。点击确认后重新校验，执行事务并落盘回执。注册表里的 `verified` 只表示查询核对，不代表已执行变更。

## 已落地的扩展点

- `backend/banking/capabilities.py`：能力定义、统一注册、参数 Schema、业务领域、read/preview/confirm 权限类型，新查询的标准事实与依据结果。
- `backend/banking/grounding.py`：同会话用户明确提及对象的依据检查。助手展示整张列表不会变成用户选中了某项；历史同时涉及多项且当前未明确时追问。
- `backend/banking/subscriptions.py`：独立的订阅报价领域处理器，只接收结构化参数，不解析自然语言期限。
- 现有账户、联系人、转账、理财、卡片、资金计划能力均纳入注册表。现有转账 `note` 参数、确认机制和回执保持可用。
- 联系人目录现支持在UI中保存备注并保留原名；聊天中尚未开放备注修改工具，也没有重新开通订阅接口。模型应引导到联系人面板，不能把联系人备注当成转账备注。

## 新业务如何接入

以联系人备注为例：定义严格的输入模型（联系人标识、备注文本），在 `bank.py` 的工具绑定表及领域映射注册；查询实现同名后台处理器，变更则在 `prepare` 和 `execute` 实现校验、确认摘要和事务更新。随后补充相关权限、歧义、取消、重复确认和回执测试。普通查询与确认卡可以复用现有前端；特殊交互再单独扩展组件。

未来新增预演工具时，需要声明其 preview 权限及保存预演的事务处理；不能因为名字像查询就允许执行资金变更。框架提供扩展位置，不会仅靠添加一句提示词自动实现业务。

## 订阅问题的结果

- 同会话取消轻办公 → 查询列表 → 询问重新订阅费用：轻办公为 25 元/月，有效订阅总额 154 元不是它的续订价格。
- 两年为 24 个月，按当前月费估算 600 元；一年半为 18 个月，估算 450 元。
- 一年与两年可分别调用报价工具，保留两次结果，不会在首次查询后丢掉后续步骤。
- 套餐、年付、折扣报价没有数据来源时，返回“资料未提供，无法确认”，不会编造优惠，也不会断言商户绝对没有套餐。
- 已执行的取消卡片用实际执行回执更新说明，前端也兼容历史卡片原先保存的“尚未执行”文字。

## 泛化能力与边界

语言理解由真实模型完成；服务、期限和套餐意图采用结构化工具参数，不为每个句式写分支。金额、对象来源和变更状态仍由后台把关。

不能保证任意复杂句式一次理解正确。当前对象依据校验以同会话中明确的服务名称、编号及已登记别名为基础；昵称、复杂指代、多个对象不明确等情况可能需要追问。订阅报价只支持整月；新的计费规则、产品套餐、预约转账或联系人备注仍需要实际后台数据和处理器。

自动化测试中的脚本模型用于验证执行机制，不能单独证明自然语言泛化。真实 DeepSeek 测试另用临时模拟数据库验证具体问法，不修改正式银行记录。
