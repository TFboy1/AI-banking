# 失败恢复与重规划

在同一对话输入“继续”“接着做”“继续刚才的操作”或“恢复上次任务”，系统读取最近一次未完成任务的持久化进度，重新核对当前业务数据并规划剩余步骤。

- 手动停止：原未完成交易仍为失败，成功交易保持成功。继续时创建新的处理尝试，关联原任务，保留原记录和回执。
- 后台关闭或重启：保存正在处理、排队及等待确认的任务，旧确认卡失效。重启后不自动重放操作，等待用户要求继续。
- 模型或业务失败：保留目标、步骤、错误和回执；继续后先检查当前情况，不能把旧错误当作现状。
- 已成功步骤保留在DAG中；失败和未执行部分重新规划，不重放旧工具队列。结果不确定的外部请求先查询核对。
- 已完成交易按恢复链与业务参数去重。付款来源或金额格式变化不能绕过重复检查；引用已成交步骤时沿用原回执，不再次扣款。
- 原计划明确多笔相同参数的交易时，按未完成笔数恢复；模型重复提出旧步骤不能增加交易笔数。
- 股票、外卖必须重新获取报价；旧报价不能直接生成恢复后的确认。理财净值、余额、限额和风险仍按当前状态重新检查。
- 所有资金操作重新确认、输入密码；红色交易重新获取并验证短信，不复用旧验证。旧确认卡不能再次执行。
- 进度按用户数据库和会话隔离；“继续”仅恢复当前会话最近一次未完成的任务。最近任务已完成时提示没有待恢复任务，避免误重做旧业务。
- 中断报告合并本任务与其恢复链的已执行回执和资金流水，按操作编号去重核对，展示整个任务已发生的资金变化。

实现主要位于 `backend/banking/recovery.py`，由 `Agent` 的启动、停止、提交与确认流程接入。原任务保存 `resumed_by`，新任务保存 `recovery.parent_task_id`、恢复链和成功DAG节点；恢复记录及卡片均持久化。

这项能力不会撤销已完成交易，也不会跳过用户确认。改变原目标或确实需要再做一笔相同交易时，应提出新的明确业务请求。
