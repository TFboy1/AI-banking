# 多平台模拟业务接入有数：可行性分析

结论：可行。把模拟证券、旅行、外卖和购物平台作为可查询、可报价、可下单的独立业务系统，由有数统一理解意图、展示选择、验证支付、记录回执。这条路线能完整演示跨平台操作，也便于测试失败、价格变化和退款。

## 平台边界

| 平台 | 数据 | 可演示能力 |
| --- | --- | --- |
| 模拟证券 | 从获授权的行情数据源获取真实股票价格；标注来源、交易日和更新时间 | 搜索、自选、历史走势、虚拟买卖、持仓和盈亏 |
| 模拟旅行 | 自建城市、航班、车次、酒店、房型和库存数据 | 搜索、组合机酒、报价、模拟预订、取消与退款 |
| 模拟外卖 | 自建门店、配送地址、菜单、库存及配送费 | 按地址搜索、筛选、购物车、订单与配送状态 |
| 模拟购物 | 自建商品、规格、库存和运费数据 | 搜索、规格选择、购物车、下单、取消与退货 |

使用独立的模拟平台名称，在界面标明演示环境；这些平台内的订单不会在真实携程、美团、淘宝或券商系统生效。股票可以使用真实行情，但成交、资金和持仓仍为模拟。

## 行情数据

例如 Tushare 提供股票历史日线接口，返回开高低收、成交量等数据。日线适合首版回放和模拟交易，不能当作实时成交价。接口需要其账户、Token 及相应访问权限；对外展示或再分发前，应确认数据供应方允许的使用范围。

- [Tushare 股票历史日线文档](https://tushare.pro/document/2?doc_id=27)
- [Tushare 接口权限说明](https://tushare.pro/document/1?doc_id=108)

API 本身只能提供其已开放且获授权的功能；例如淘宝官方接口涉及用户数据时需要应用和用户授权。自建模拟平台可以自行定义接口，无需申请真实平台的下单权限。

- [淘宝开放平台授权文档](https://developer.alibaba.com/docs/doc.htm.htm?articleId=102635&docType=1&treeId=1)

## 推荐执行流程

用户指令 → 意图与参数提取 → 平台搜索 → 展示候选 → 用户选择 → 后台生成有效期报价 → 展示订单及费用 → 用户确认、选择付款账户、密码／短信验证 → 执行模拟订单 → 返回真实的本地执行回执。

查询可以自动完成；存在歧义时补充城市、日期、规格、配送地址等信息。支出沿用有数现有支付验证，由后台统一判断风险。大模型只调用白名单工具，价格与成功状态都由业务系统提供。

## 接口约定

每个平台至少提供搜索、详情、报价、创建订单、查询订单、取消／退款六类接口。报价包含商品或服务编号、规格、数量、完整费用、币种、库存版本和过期时间。订单携带同一个幂等键；超时后先查订单状态，再决定是否重试。

账户、支付和总账集中在有数，模拟平台保存自己的库存与订单。支付确认绑定具体报价和用户；不得让平台自行覆盖余额，也不能让模型自行填写扣款金额。四个平台之间用独立适配器连接，新增平台只增加工具和适配器，不修改聊天主流程。

## 重点难点

1. 跨系统一致性：不能只按“扣钱→创建订单”直接串行。建议先生成待支付订单并锁库存，再冻结资金，确认订单后入账；失败释放冻结。对超时和部分成功建立状态查询、对账及补偿流程。
2. 交易幂等：同一请求重复点击、模型重试或网络超时，都只能产生一次扣款、一笔订单。
3. 行情时效与成交规则：真实行情有交易时段、停牌、涨跌停、交易单位和可能的数据延迟；首版应限定市场与交易规则，缺失或过期数据停止成交。
4. 任务规划：复杂行程可分解为搜索交通、搜索酒店、预算比较、确认各项订单等步骤；需补显式依赖、失败状态和补偿，不能把所有平台的成功视为天然原子操作。
5. 用户隔离：平台授权、地址、订单、资金和回执都绑定当前用户；商品描述只当作数据，不能作为新的系统指令。

## 建议落地顺序

先建一个通用模拟商城，打通搜索、报价、确认、扣款、订单、退款全流程；再接入旅行和外卖的专有规则；最后接真实行情和模拟证券交易。四个站点可以共用底层服务，分别展示各自页面，无需一开始就运行四套独立后端。

当前已完成理财模拟净值和历史展示；本分析所述四个平台及其订单接口仍是后续建设方案。
